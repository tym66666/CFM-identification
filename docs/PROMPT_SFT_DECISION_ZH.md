# Prompt 已经够好时，为什么不必急着模仿 UniCo？

当前研发目标是：让业务人员提交直观描述和配套资料，由模型生成准确的因果问题草稿，让现有严格识别库继续提供数学保证。

UniCo 的主要训练例子来自**已经给定的 SCM/因果图及条件概率分布表（CPT）**，从中计算答案并转换为符号、代码和自然语言形式。它主要在提升模型的因果推理表现，并非专为“客户文件 → CFM 网络因果规格”而设计。

如果现成 API 模型在明确的 Prompt 和格式/证据审核下表现足够好，那么没必要为了项目形式而微调：

1. 先测现成模型。分别测目标分类、目标数量、引用、A4/A5 乱补、分配机制误读、业务资料冲突，以及陌生行业和文件格式。
2. 有少量错误时先修 Prompt/数据提取/validator，而不是把可修复的工程问题归咎于模型能力。
3. 只有持续出现的系统性语义/数学错误、成本需求、私有部署需求，且高质量标注数据足够时，才评估微调或蒸馏。
4. 微调后仍然保留独立数学定理和证书验证；训练不能让 LLM 成为因果假设的最终许可者。

## 今天的数据集也值得保存

它既可做 **Benchmark（不训练）**，也可在未来确有必要时变成训练数据。但必须对两者严格隔离。我们的评测要留出从未用于训练的真实风格业务材料、网络设置、目标组合和表达形式。

## 当前 的评测不能证明什么

`evaluation/multiquery/business_queries.json` 有 8 组人工审阅的业务问题及目标类型参考标签。离线 reference fixture 仅检验评分器、Prompt 输出形状与原文引用检查是否运转；**即使得分 100%，也不是 LLM 模型准确率，更不是数学识别正确率。**

在线评测 `--provider openai-chat` 可在你本地配置 API Key 后运行；程序返回的目标类型精确率/召回率也不能替代对完整因果目标、A4、A5、A6 的人工数学审核。
