# 已有设计与暴露接入后的真实 LLM 验收

日期：2026-10-31。工作源码为本目录所属的 `causal_idfm`，没有修改或同步 GitHub 发布副本。

**结论：已有 D/E 的工程接入和真实模型首读可靠性必须分开。此次严格首读验收未通过；有一条经明确复查、独立审核后进入 R1a 并重放成功的正例，以及一条首轮正确阻断的缺条件负例。不能宣布自然语言业务已稳定接通。**

采用当前推荐读取配置。链路为实际 A0 → 开发者逐字段语义与来源审核 → 实际事实读取 → 来源/科学条件审核 → 原生求解和独立重放。A0 未通过者不使用人工参考替换后继续。科学条件已经在合成研究方案中声明，后续许可由开发者单独审核，不由 LLM 自批。

## 两次明确定位复查

每个模型仅追加一次事实重读，沿用已有复查接口。只指出原文字段位置和现有合同，不发送参考值、识别答案或新条件。

- **DeepSeek，D2/E4 自身效应：仍失败。** 逐店 `(Y_i, 完整处理向量)` 的总体分布仍被写成全部结果向量的联合分布；研究背景的局部引用也未补全。审核继续阻断，没有调用数学后端。
- **LongCat，D4/E3 同伴效应：复查后 POINT，独立重放通过。** 模型补上了一条背景备注的原文引用，其他业务字段均未改变。开发者依据原有 `reading_note_review` 合同，把“未指定协变量取值”的真实说明判为 `NONBLOCKING_COMMENT`，没有要求补一个不存在的背景层，也没有删除备注。随后完成完整来源、科学条件和方法审核，调用 `R1A_COMPOSITION`，得到六店两端共 12 个条件均值项的识别式，所有所需支持为正，证书重放成功。

这条 LongCat 结果属于**复查和明确审核后的成功**，不计入首答成功。首轮把备注视作字段归属问题的审核原件和后续裁决理由均保留；首答的引用缺失也保留为失败。没有由评测程序补引用或修改模型返回。

## 本轮发现的边界

1. **读取错误仍是真实阻碍。** 典型问题为：总体信息重复填入样本记录；局部处理状态填入固定背景；均值暴露充分性填入标准化分布；整簇抽签与分层名额混淆；主政策字段混入另一政策；对象名称展开却遗漏名册引用；将逐店总体分布升级为全部结果联合分布。
2. **公开格式与内部接收有不一致。** LongCat 的一条负例使用 `assignment_family=COMPLETE_RANDOMIZATION` 并将不完整分配律记作 `MISSING`；公开 Schema 允许，内部 `information_design` 拒绝。该回答还有其他误读，因此修好解析边界也不能直接把整题改记成功。
3. **缺参数与未覆盖的状态边界需要处理。** `assignment_rule_available` 公开含义是原文是否提供完整分配律；模型在明确缺名额时填 `false`。当前局部效应适配器把它解释为排除适用范围，先返回 `ADAPTER_NOT_CONNECTED`，而非待补参数。这不是数学 Core 的问题，不能仅靠要求模型填 `null` 掩盖。该回答另外有总体信息类型错误，仍需重读。
4. **可选备注应走已有独立裁决。** 未指定额外协变量层不等于用户漏交必需条件。这里有可用的备注审核合同；不能把所有备注统一当覆盖缺口，也不能无审核忽略真实缺项。

下一项代码工作应先修第 2、3 项的接收/状态合同，保留真实缺项、明确拒绝、矛盾和数学未覆盖的区分，再用保留回答重放与少量新题验证。无需为本轮结果改数学 Core，也不应立即再堆一轮长 Prompt。

## 后续本地接口修复与原回答重放

本节记录上述 API 实验结束后的代码修改；不覆盖原始成绩，也不计为新的 LLM 测试。

已修复两处确定性的接收/状态问题：

1. **允许保留“知道设计类别，但资料缺少参数”。** 例如原文明确按固定名额抽签，却没有提供名额。A0 内部草稿现在分别保留已知设计类别、未确定的分配律和带原文引用的缺项说明；缺项说明不会成为已知分配律或科学许可。来源错误仍须复查；旧协议没有缺项说明的记录保持原有序列化表示。
2. **完整分配资料未提供时归为需要补充信息。** 局部效应、单政策均值、两政策差值共同使用该规则，`false` 和 `null` 原值不改写、不补参数。明确拒绝科学假设、相互矛盾的声明、非法参数和来源被否决仍分别阻断，不能借此调用数学后端。

职责分别落在 `cfm_id_llm` 的草稿/接收合同，以及 `cfm_id` 的设计公共适配和业务分派。相对实验前记录，运行代码仅修改 `schemas.py`、`compact_formulator.py`、`network_design_adapter.py`、`network_effect_dispatch.py`、`network_policy_dispatch.py`。数学 Core、冻结业务与参考、推荐 Prompt 均未修改；本轮没有 API 调用，没有同步或推送发布副本。

验收结果：

- **原始 28 份 A0 回答重放：** 请求文字和模型原始输出全部保持不变。仅 `longcat_quota_missing_1_a0` 从内部格式拒绝变为可进入语义审核；它把同伴处理状态填进背景的错误仍被拒绝，不能算整题成功。
- **真实缺项回答重放：** 缺分配资料从 `ADAPTER_NOT_CONNECTED` 改为 `NEEDS_INPUT`。该回答另有总体信息误读；带入原来源审核后，最终仍为 `READING_RECHECK_REQUIRED`，没有调用数学后端。
- **真实成功回答重放：** 先前 LongCat 复查后的同伴效应仍为 `POINT`，识别式和持久化证书完全一致，独立重放通过。
- **相关离线验收：** 356 个不同测试及 17 个子测试通过，范围包括接收合同、设计/暴露入口、政策均值与差值、局部效应、兼容性和验收登记。不是全量发布验收。首次运行有一处新增测试夹具使用旧来源引用、两处 Windows 临时目录权限失败；修正夹具/指定工作区临时目录后，对应三项分别重跑通过，保留首次记录。数学与运行实现未为这些测试改动。

重放记录为本地 本地验收产物（不分发），测试明细见同目录 `INTERFACE_FIX_TESTS.json`。原 `SUMMARY.json`、模型输出及人工审核记录保持不变。新增关键检查已经登记到现有 S34、S88 验收责任项，没有另起一套重复流程。

后续模型可靠性可以以“代表性冻结业务达到约 80% 以上”作为阶段目标，无需追求穷尽所有措辞；但必须分别报告首答/复查、正例/缺条件负例，以及格式/语义/引用/最终执行，不能用某个单字段准确率代替完整业务成功率。这个目标不改变科学审核和证书的通过标准，也不表示本报告已有 80% 的实测结果。下一轮应采用少量未参与调试的完整业务验证这两处修复；只有仍阻断主线的合同或实现问题才继续修改。

## 接口修复后的四份新材料：真实首答与一次复查

这轮使用未参与上述代码调试的两个合成业务情境，各有一个正例和一个缺条件负例，共四份材料。输入、私有参考、科学审核依据和调用上限先冻结，再调用模型；没有根据输出补条件或改题。它是开发验收，不是独立盲评或 NBIB 总体准确率。

| 业务 | 原问题与条件 | 调用前参考结果 |
|---|---|---|
| 洗衣门店直接效应 | 四店形成固定合作环，均匀抽两店使用排班助手。恰好一家合作店使用时，比较本店使用减未使用的等待时间，再对四店等权平均；其余安排按原试点条件概率平均 | POINT，证书重放通过 |
| 洗衣门店缺名额 | 同一问题，仍明确均匀固定名额抽签，但资料未提供具体名额 | NEEDS_INPUT；不能默认补成两店 |
| 维修网点政策差值 | 六店形成固定合作链，两组分别均匀抽一店、两店。比较两张明确的完整使用名单下，六店等权平均等待时间的差 | POINT，证书重放通过 |
| 维修网点条件待定 | 同一问题，实际观察结果与实际完整安排下潜在结果一致的条件尚未决定是否采用 | NEEDS_INPUT；不能替研究者批准 |

材料同时包含一次试点记录和单独声明的符号总体联合分布，二者职责分开。全部是合成研究材料，不包含真实企业资料。每个模型对四份材料各答一次；失败链路最多一次 A0 定位复查、一次事实定位复查。复查只发送原文字段位置及既有合同约束，不发送参考答案、求解结果或替换值。

模型为 `deepseek-v4-flash` 与 `LongCat-2.5-Preview`。沿用现有 JSON、非流式、关闭 thinking、300 秒等待上限的调用配置，三个 DeepSeek 凭据合并统计。这不是对两个模型全部配置或一般推理能力的排名。

## 显式定义依赖接口的四次事实读取对照

本地修复确认了一处接口缺口：已有实验合同区分“直接主张来源”和“名册/编码定义依赖”，但没有覆盖均值充分性记录中的评价名单。新增显式实验合同 `network-policy-record-definitions-1` 补齐这一位置，复用共同登记、来源审核、科学审核与证书重放。没有修改数学 Core、A0 Prompt、推荐配置或原始业务；没有自动补引用、补条件或改模型答案。

先冻结四次调用，再沿用上节维修网点的正负材料和已通过人工审核的 A0，分别让两模型重新读取事实。原材料、来源目录、A0 候选与 A0 请求逐项核对不变；DeepSeek 负例使用的是上一轮复查通过的 A0，其余三条使用上一轮首答通过的 A0。**这是同一开发材料的接口对照，不是新的盲测，也不计为整题首答准确率。**

| 模型 | 事实格式 | 事实语义 | 引用覆盖 | 条件齐全正例 | 条件待定负例 |
|---|---:|---:|---:|---|---|
| DeepSeek V4 Flash | 2/2 | 2/2 | 2/2 | POINT，独立重放通过 | NEEDS_INPUT，未调用数学后端 |
| LongCat 2.5 Preview | 2/2 | 2/2 | 2/2 | POINT，独立重放通过 | NEEDS_INPUT，未调用数学后端 |

四份回答均由开发助手逐字段核对原文和实际引用；模型自己声明定义依赖，审核没有替其补齐。两条正例完成两政策差值的原生审核、计算与证书重放；两条负例保留一致性条件 `UNDECIDED`，无证书。四次均 HTTP 200，无传输重试、无事实复查。DeepSeek 用时约 53–54 秒，LongCat 约 12 秒；这一小样本不作速度或能力排名。

相关离线验收共 **245 个不同测试通过**，包括 POINT/PARTIAL 均值及差值、缺引用与拒绝条件、审核绑定、配置与兼容检查。首次有一项 R2 手写参考夹具扩充名单后未同步声明定义依赖，运行接口正确拒绝；只修正该夹具并重跑通过，首次记录保留。全部 14 个旧配置的 28 份均值/差值请求逐字保持一致。这不是全量发布验收。

完整输入输出和审核在 `outputs/definition_contract_acceptance/`，`SUMMARY.json` 保留分层结果，`ACCOUNTING.json` 保留次数，`OFFLINE_SUMMARY.json` 与两份测试 XML 保留离线记录。本轮 DeepSeek 第 1/2/3 把凭据分别新增 1/0/1 次，LongCat 新增 2 次；剩余授权分别为 171/138/69、105 次。密钥仅供认证进程载入；未复制到发布目录、未提交或推送。

**仍未解决：** 局部效应 A0 的背景归属、已知设计但缺参数时的状态读取，以及冻结新业务的完整首答可靠性。本次结果说明引用接口值得继续验收，不能把上节 25% 整题结果改写为 100%，也不足以更换推荐配置。下一轮应固定该候选配置，在新完整业务上检查 A0 到识别的整条链路，继续分别记录首答、显式复查和正确缺项停止。

## 固定候选配置后的新业务全链路验收

固定 `network-policy-record-definitions-1`，其他读取设置沿用推荐配置。在本次任何 API 调用之前，冻结两组新合成业务、四份完整材料、预期结论和复查上限。每个模型各读四份 A0；只有实际回答通过审核才进入真实事实读取、来源与科学条件审核、原生识别和证书重放。每阶段最多一次定位复查，不发送参考答案或求解反馈，不改题、不补条件、不更换模型回答。本轮为开发助手审核，不是独立盲评。

| 新业务 | 目标与材料 | 调用前参考 |
|---|---|---|
| 共享单车维修站：完整条件 | 六站固定合作环，均匀抽三站启用工单调度助手；评价明确三站启用、三站未启用的完整政策下，六站等权平均维修小时数。暴露记录合作站启用数量 | POINT / replay |
| 维修站：缺名额 | 同一目标，已知均匀固定名额抽签，但材料未提供名额数 | NEEDS_INPUT |
| 面包门店：完整条件 | 六店固定合作环，三个两店组各独立抽一家；暴露按合作店启用比例分三档。比较两张明确完整名单下的六店等权平均每日报损公斤数，方向为方案一减方案二 | POINT / replay |
| 面包门店：条件待定 | 同一目标，一致性条件尚未决定是否采用 | NEEDS_INPUT |

原文将一轮试点记录与另行声明的符号总体联合分布分开。有限记录没有声明完整覆盖六个单位；名册和评价名单不能补出记录覆盖。自然业务目标、设计、科学声明等原文全部保留在 本地验收产物（不分发）；私有参考始终未发送给模型。

### 每条链路实际停在哪里

| 业务 | DeepSeek | LongCat |
|---|---|---|
| 维修站正例 | A0 漏填 intervention，复查补回；事实首答额外声称“未给数值所以不能识别”，事实复查删除无来源结论。全部变化重新审核后，**POINT / replay** | A0 普通字符串格式经复查修正；事实把一轮记录的覆盖名单扩成六站，复查只增加名册引用，范围仍无依据。**READING_RECHECK_REQUIRED** |
| 维修站缺名额 | 首答将缺参数的分配律记为 STATED，复查改为 MISSING；事实保留固定名额 null 和规则不完整，最终 **NEEDS_INPUT** | A0 和事实首答完整保留缺名额，直接 **NEEDS_INPUT** |
| 面包正例 | 主政策字段混写两个相反名单，A0 复查仍未修正。**CHECK_BLOCKED**，未调用事实模型 | 两端、方向和科学条件读对；可选 first_stage_exclusion 写 NOT_STATED 却带来源，违反状态/来源配对规则，复查未修正。**CHECK_BLOCKED** |

实际成功的维修站政策为按固定顺序的 `(1,0,1,0,1,0)`，每站权重 `1/6`。原生 `R1B_FULL_ASSIGNMENT` 检查其历史概率为 `1/20`，返回六个完整安排条件均值的等权识别式，并独立重放证书。结果是符号公式，`numeric_value=null`，没有凭空计算维修小时数。调用前的两个参考 POINT 没有计入模型成绩；所有缺项或失败链路均未发出数学证书。

### 结论与留存

本轮最终完整通过为 4/8，尚未达到约 80% 的阶段目标。四份题仅代表两个独立情境，不能用于一般模型排名或 NBIB 总体准确率。背景误填没有在这组题中重现，不代表局部效应的背景问题已解决。

有依据继续保留显式定义依赖，但它不能解决全部 A0 重复字段或有限记录范围误读。面包正例还暴露出诊断可读性不足：内部拒绝码明确是 `FIRST_STAGE_EXCLUSION_SOURCE_STATE_REQUIRED`，公开复查只给 `/first_stage_exclusion` 的 `value_error`；初始系统说明虽已有 NOT_STATED 引用为空规则，JSON Schema 本身没有表达这一交叉约束。不能把复查失败完全归为数学能力，也不能直接绕过验证器。本轮只记录，未在冻结实验中改代码或增加提示。

共 **22 次实际 API 请求**，DeepSeek 11 次（三把为 6/3/2），LongCat 11 次；全部 HTTP 200、合法 JSON，无超时或传输重试。合法 JSON 不等于通过字段格式。剩余授权为 DeepSeek 165/135/67 次，LongCat 94 次，无需追加授权。密钥仅由认证进程载入，不输出、不记录。

完整证据在 本地验收产物（不分发）：`PLAN.json`/`PROTOCOL.json` 为冻结配置和上限；`requests/`/`live/` 为请求及原始输出；`audit/` 为首答、全量变化、来源、科学审核及最终执行记录；`SUMMARY.json`/`ACCOUNTING.json` 为分层成绩和次数。已验证冻结运行源码、原材料、参考和实际请求一致，模型原答未改。审核脚本曾提交一条过短的理由而被拒绝，修正审核理由后再提交，原失败记录保留；这不修改模型回答，也不涉及放宽审核。数学 Core、Prompt 与推荐配置未变，未同步发布目录、未提交或推送。

下一步应优先整理有证据的字段/接口负担：主政策与处理端的重复表达、有限记录范围的未知表示，以及交叉字段拒绝原因能否准确传到公开诊断。保留原审核边界，先做可复现的接口检查；本轮到此停止，不继续追加调用直到题目通过。

## 主政策、有限记录范围与诊断接口整理

本地新增显式实验组合 `single-action-target-1` + `network-policy-scopes-1`，推荐配置未变。数学 Core、Estimation/Policy、发布副本均未改；没有提交或推送。

| 接口 | 当前规则与验收边界 |
|---|---|
| 主政策重复表达 | 政策均值和两政策比较只从 `semantics.intervention` 读取主端；旧 `policy_assignment` 是有记录的同值兼容视图，模型不得重复填写。比较基准和方向保持独立。缺主端不从目标句补写 |
| 有限记录范围 | 信息存在的引用、覆盖范围的引用、对象名册定义分开保存。范围未说明使用 `UNSPECIFIED` 和空坐标；明确范围必须有直接原句。总体分布与有限记录可以同时存在，有限记录不升级为总体信息 |

实际残留如下：

- DeepSeek：两份 A0 首答仍输出已取消的重复字段；复查修正格式，但负例另外误把门店调拨关系写成固定背景。单政策事实首答和复查均漏掉有限记录；差值事实先把三个固定名额组读为两阶段混合，复查又改为两组设计，且仍漏有限记录。
- LongCat：三个 A0 均通过。事实中出现有限记录遗漏、从名册扩出全体覆盖、遗漏公斤单位，以及把请求说明元数据复制进输出。差值正例复查正确保留了有限记录的未知范围，但结果单位及样本性质备注仍错误；不能据部分修复批准整题。
- 一致性待定负例中，LongCat 保留了正确的 `UNDECIDED`；由于同一回答仍有范围及单位错误，不能算完整负例通过。所有误读均阻断，没有真实模型回答获得数学证书；离线参考的 POINT/PARTIAL 不计入模型成绩。

### 删除继承的矛盾规则后，仅补测 A0

核查上述实际请求发现：新 Schema 取消了重复字段，但继承说明仍说“完整政策的主方案放 policy_assignment”，随后又追加相反规则。最终代码在新实验 profile 中**替换被废弃的原规则**，不再叠加提醒；旧 profile 的请求不变。

在同一维修站材料上仅补测两个 A0 请求：DeepSeek 仍输出重复字段，格式未通过（语义和引用保留正确）；LongCat 三项通过。未做事实读取或数学执行，不能把它写成全链路成功。此处说明矛盾已经消除，但模型遵守新结构仍无稳定证据；本轮不再追加 Prompt 版本。

本轮合计 **20 次调用**，DeepSeek 10 次（三把 5/3/2）、LongCat 10 次。剩余授权分别为 160/132/65、84 次。密钥仅由认证进程载入，不输出或记录。

证据目录：本地验收产物（不分发） 保存接口对照、331 项测试与最终相关重跑、兼容对比、原始请求／回答、逐字段及变更审核、`SUMMARY.json` 和 `ACCOUNTING.json`；本地验收产物（不分发） 保存最后两次仅 A0 检查。18 次对照期间全部 383 个运行 Python 文件保持不变；最后两次使用另行冻结的最终源码。准备脚本曾有参考会话绑定、返回类型及反馈路径错误，均在请求前修正并留存；没有为修复脚本改写模型答案。

**结论：接口的字段归属和拒绝边界已完成本轮定向验收，但真实业务读取尚未稳定，新组合暂不提升为推荐默认。** 剩余重点是完整记录清单在两阶段间的保留，以及模型对设计、量纲和背景的误读；不能用程序兼容通过替代这些实测结果。
